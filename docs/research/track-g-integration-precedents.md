# Research Brief — Track G: wger Integration Patterns & Precedents

## Key Findings

1. **wger's own mobile app is the canonical API consumer — and it just went offline-first.** The Flutter app (`wger-project/flutter`, v2.0.3+240) migrated in 2025–2026 from REST-polling to **PowerSync** (Postgres logical replication → on-device SQLite). Its stack: `powersync ^2.3.2`, `drift ^2.34.2` (SQLite ORM), `flutter_riverpod ^3.3.2`, `connectivity_plus`, `flutter_secure_storage` (token storage), `freezed`/`json_serializable` codegen models, `http`, `flutter_zxing` (OFF barcode scanning), `video_player` (exercise videos). Server 2.6 added a `powersync` service to the prod docker-compose stack; setup friction is real (see Risks).
2. **The REST API (`/api/v2/`) remains the stable integration surface** and is what every third-party consumer uses. Auth: Token (`Authorization: Token <key>`) or JWT (added v2.1, now also used by PowerSync auth). Public endpoints (exercises, muscles, equipment, ingredient info) are readable without auth. API is documented with OpenAPI/redoc (drf-spectacular, issue #1127) — **clients can be code-generated**.
3. **API has breaking changes between minor releases — pin and gate.** Release 2.5 removed `/api/v2/ingredient/search/`, `/api/v2/exercise/search/`, `/api/v2/variations/`, `/api/v2/weightunit/`; moved exercise variation into a field on the exercise model; added `unit_type`/`multiplier` to `setting-repetitionunit`. There is **no announced API v3**; roadmap lives at `github.com/orgs/wger-project/projects/6`. A `/api/v2/min-app-version/` endpoint exists to force client upgrades — precedent for version-gating your own client.
4. **Self-hosting is the mature, blessed pattern**: `wger-project/docker` prod compose = gunicorn + nginx + postgres + redis + celery worker/beat + (new) powersync. Third-party guides cite **2 GB RAM min / 4 GB recommended, 10 GB disk**. Must run on its own (sub)domain (no subdirectory). Persistent volumes: `postgres-data`, `redis-data`, `celery-beat`, `static`, `media`.
5. **Known third-party consumers of the wger API** (all use plain REST + token, none fork the backend): `democratize-technology/node-red-contrib-wger` (Node-RED nodes), `Juxsta/wger-mcp` (MCP server for AI assistants, MIT), openScale (community request to push weight entries to `wger.de/api/v2/weightentry/`). The public `https://wger.de/api/v2/` is routinely used as a default endpoint by hobby integrations.
6. **wger itself is a downstream consumer of Open Food Facts** — it syncs OFF data into its own DB (v2.5: bulk sync via pre-generated DB dump preferred over paginated API; live OFF fallback on barcode scan cache-miss, #1012/#1348). This validates the "mirror-and-cache upstream data, fall back live" pattern.
7. **Complements/alternatives verified**: USDA FoodData Central — public domain (CC0), free api.data.gov key, **1,000 req/hour/IP**, 429 + 1h block on excess; Open Food Facts direct — ODbL (attribution + share-alike on derived DBs), **15 req/min/IP product reads, 10 req/min/IP search** (no search-as-you-type), custom User-Agent mandatory; ExerciseDB — RapidAPI gateway, tiny free tier (~10 req/day reported), GIF assets; `exercisedb.dev` open self-host variant (AGPL-3.0, claimed 11k+ exercises); `yuhonas/free-exercise-db` — public-domain static JSON, 800+ exercises with images; API Ninjas — metadata only.

## Concrete Facts

- **Flutter app deps** ([pubspec.yaml](https://raw.githubusercontent.com/wger-project/flutter/master/pubspec.yaml)): `powersync`, `drift`, `drift_sqlite_async`, `riverpod_annotation`, `connectivity_plus`, `app_links`, `flutter_secure_storage`.
- **Docker setup** ([wger-project/docker](https://github.com/wger-project/docker), [docs](https://wger.readthedocs.io/en/latest/installation/docker.html)): one-time `docker compose exec web ./manage.py setup-powersync-storage` (idempotent); `JWT_PRIVATE_KEY`/`JWT_PUBLIC_KEY` via `./manage.py generate-jwt-keys`; `PS_STORAGE_PG_URI`, `PS_JWKS_URL` env vars; Postgres needs `wal_level=logical`.
- **API endpoints**: `/api/v2/exerciseinfo/`, `/api/v2/ingredientinfo/` (search-capable replacements for removed `/search/` endpoints), `/api/v2/routine/`, `/api/v2/weightentry/` (POST `{date, weight}`), `/api/v2/min-app-version/`, `/api/v2/login` (token obtain).
- **wger 2.5 nutrition model additions**: `is_vegan`, `is_vegetarian`, `nutriscore` fields on Ingredient; OFF serving sizes ("1 Serving (2 biscuits)") auto-imported; `SYNC_INGREDIENTS_CELERY` bulk dump sync.
- **wger Flutter app license**: AGPL-3.0+ **with app-store exception** (section 7 additional permission); exercise/ingredient data CC-licensed per-item (images CC-BY-SA 4.0).
- **OFF API** ([docs](https://openfoodfacts.github.io/openfoodfacts-server/api/)): 15 req/min reads, 10 req/min search, per-IP (per-user if calls come from client devices); bulk use → download CSV/JSONL dumps or self-host Product Opener.
- **FDC** ([api-guide](https://fdc.nal.usda.gov/api-guide)): CC0 1.0, attribution requested; `X-RateLimit-Limit`/`X-RateLimit-Remaining` headers on every response.

## Integration Implications for AquaZeroFit

1. **Recommended pattern: server-side read-only mirror, never client-direct.** Consume wger as AquaZeroFit's `apps/api` → wger REST (self-hosted or wger.de) with a server-held token; normalize into your document store (Cosmos/local JSON) behind your own zod schemas in `packages/shared`. This matches every observed consumer (Node-RED, wger-mcp, openScale) and keeps AGPL code and CC data quarantined outside your proprietary codebase.
2. **Adopt wger's "dump-first, API-fallback" precedent** for both exercises and ingredients: periodic bulk sync job (scheduled Automation) + live fetch on cache miss (wger's own OFF pattern). OFF's 15 req/min cap makes client-direct lookups infeasible at scale; wger's mirrored `ingredientinfo` endpoint is the escape hatch.
3. **Offline/sync strategy**: wger's PowerSync migration shows where the ecosystem is heading, but PowerSync requires Postgres logical replication — incompatible with AquaZeroFit's document-style Cosmos/JSON store. Steal the *pattern* (drift-style local cache + FIFO upload queue + connectivity gating), not the tool. For the Telegram Mini App, cache wger exercise/ingredient payloads in your API layer instead.
4. **Version-gate your integration** like wger's `/min-app-version/`: record the wger server version per sync, pin to a tested release (2.5/2.6), and treat minor upgrades as migrations (2.5 removed four endpoints without a deprecation period).
5. **Nutrition stack recommendation**: wger/OFF for branded/packaged barcode foods + USDA FDC (CC0, no share-alike) as the lab-grade reference layer for whole foods — the combination mitigates ODbL share-alike exposure if you build a derived food DB (mixing OFF into a proprietary DB triggers ODbL; FDC does not). wger's new `nutriscore`/vegan flags are worth importing for your deterministic allergen/diet filters — but keep allergen decisions on your code, not wger data, per your safety invariants.
6. **AGPL hygiene**: self-hosting unmodified wger as a separate network service is safe; do not copy wger/Flutter code into the repo (AGPL-3.0+). CC-BY-SA exercise images require attribution; show per-exercise license metadata in UI (wger itself does this).
7. **Self-hosted wger for staging/CI**: `wger/demo` image or dev compose gives a disposable fixture server (default `admin`/`adminadmin`, daily-reset test server `https://dev.wger.de` also usable) — zero-cost contract testing against the real API.

## Risks / Open Questions

- **PowerSync setup friction is a known incident class**: after the 2.6 docker-compose update, self-hosters hit "Sync service unavailable" in the mobile app due to undocumented `config-powersync/*.yaml`, `PS_STORAGE_PG_URI`, and replication requirements (docker issue #156, Proxmox issue #15187). If AquaZeroFit ever self-hosts wger 2.6+, budget ops time for this.
- **No deprecation policy**: 2.5's endpoint removals had no overlap window — confirm per-release changelogs before upgrades; no API v3 announced but the v2 surface keeps shifting.
- **CC data licensing granularity**: licenses are per-exercise/per-image; bulk redistribution rights need item-level checks (each child item may differ).
- **Unverified items** (couldn't fetch the page this turn): exact throttle rates on wger.de's public API (readthedocs "Using the API" page URL structure changed; endpoint-level rate limits not confirmed) and the current contents of the public roadmap board `orgs/wger-project/projects/6` (requires JS to view). Recommend a follow-up check before finalizing the integration contract.
